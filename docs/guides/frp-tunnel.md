# 樱花 FRP 隧道配置

目标：把 PC 上 `127.0.0.1:8765` 的 TCP 服务映射到一个公网入口，让手机能拨进去。**只在 PC 上配**，手机不装任何穿透软件。

## 为什么用 TCP 而不是 HTTP 隧道

dsh-mesh 跑的是 WebSocket。樱花 FRP 的 HTTP/HTTPS 隧道会介入 HTTP 语义（改写头、处理 TLS 终止），而本插件只需要一根能传字节的管道。TCP 隧道最干净：

- PC 侧加密（应用层始终加密；开 TLS 后连握手也加密）；
- 隧道只做转发，看不到明文；
- 手机端 url 用 `ws://` 还是 `wss://` 取决于 PC 是否开 TLS，与隧道类型无关。

## 1. 在樱花园面板创建隧道

1. 登录樱花园（`https://www.natfrp.com/`）→ 隧道列表 → 新建隧道。
2. 隧道类型选 **TCP**。
3. 本地地址填 `127.0.0.1`，本地端口填 `8765`（与插件配置的 `server.port` 一致）。
4. 节点选离你近的，带宽按需要。
5. 创建后，面板会给出：
   - **隧道 ID**
   - **访问地址**（形如 `域名:端口`，或 `节点域名:远程端口`）
   - 该隧道所属的 **访问密钥（token）**

## 2. 在 PC 上启动隧道

樱花 FRP 的客户端配置里，这条隧道需要：

- 隧道 ID
- 访问密钥
- 或直接写 `[common]` + `[[proxies]]` 段的 `frpc.ini`

启动后，PC 的樱花客户端会主动连到樱花服务端，把 `127.0.0.1:8765` 暴露成公网 `域名:端口`。

**这一段没有改 dsh-mesh 的任何东西**：插件仍然只监听 `127.0.0.1:8765`，暴露由隧道负责。

## 3. 把公网地址填进插件

PC 端自己不需要填（它是监听方）。手机端的 `peers` 要填：

```yaml
peers:
  - alias: pc
    url: ws://<樱花访问域名>:<远程端口>/dsh-mesh
    autoConnect: true
```

- 路径固定为 `/dsh-mesh`（listener 只服务这一个路由，其它路径直接 404）。
- 协议是 `ws://` 或 `wss://`；**不能是 `http://`**。插件会拒绝非 ws/wss 的 url。
- 如果 PC 开了 TLS（`server.tls.enabled: true`），这里必须写 `wss://`，并且手机端要配 `server.tls.fingerprintSha256`。

## 4. 验证隧道

在**手机**的 rootfs 里（或任何一台外网机器）先确认端口可达：

```bash
# 能连上就说明隧道通了（不要求一定返回内容）
curl -sS -o /dev/null -w "%{http_code}\n" "http://<域名>:<端口>/dsh-mesh" --max-time 8
```

预期是 `400`（因为 GET 不是 WebSocket upgrade，listener 会拒绝）。如果是连接超时 / 拒绝，说明隧道或端口不对，先别去调插件。

> 这一步很关键：`400` 是**正确的失败**，它证明 TCP 层通了，失败发生在 WebSocket 升级层。

## 5. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 外网 `curl` 超时 | 隧道未启动 / 端口写错 / 免费节点限速到不可用 | 在樱花园面板确认隧道状态为在线；换节点 |
| `curl` 返回 404 | 路径不是 `/dsh-mesh` | 检查 url 拼写 |
| 连上后几十秒断 | 免费隧道空闲断开或流量限制 | 保持心跳（插件默认 20s 一次 ping，已能维持） |
| 手机能连但握手失败 | 配对没做，或设备 id 对不上 | 看 `mesh_status` 的 `lastError` |
| 时好时坏 | 移动网络 NAT 与隧道叠加 | 重连退避会自动恢复；必要时把 `heartbeatIntervalMs` 调到 10s |

## 6. 安全边界（重要）

樱花 FRP 的 TCP 隧道**不终结 TLS**。这意味着：

- 隧道运营方能看到**字节流**（但看不到内容——应用层是 AES-256-GCM 密文）。
- 未开 TLS 时，隧道能看到 dsh-mesh 的 **hello 帧**：其中包含设备 id、公钥、一个随机数与其签名。**不含**配对密钥，也不含任何文件内容或命令。
- 开 TLS 后，连 hello 也是加密的。

因此默认配置（无 TLS）仍然满足「公网连接必须加密、不能明文远程 Shell」的要求，因为：

1. 所有业务帧都加密；
2. 未经配对的对端在握手阶段就被拒绝，一个字节的业务数据都不会发出；
3. 没有 shell——`mesh_exec` 只接受程序名 + 参数，解释器和 shell 被明确拒绝。

如果你的威胁模型包含"隧道运营方主动做中间人"，请开启 TLS 并固定指纹。

## 7. 不用樱花 FRP 的替代方案

插件不绑定樱花 FRP，任何能把 TCP 端口映射到公网的方案都能用：

- **同一局域网**：手机直接连 `ws://<PC 内网 IP>:8765`，把 `server.host` 临时改成 `0.0.0.0`（仅在可信网络下这么做）。
- **其它 TCP 隧道服务**（frp 自建、ngrok TCP、Cloudflare Tunnel 的 TCP 模式等）：配置方式相同，只是 url 不同。
- **反向拓扑**（PC 连手机）：只在同一局域网可行，因为手机不暴露公网端口。

关键约束只有一条：**两端至少有一端能被另一端拨到**。v0.1 的推荐做法始终是"手机拨 PC"。
